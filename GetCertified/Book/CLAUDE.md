# Book feature

The Book tab holds the user's training list: the trainings they added from Courses. It works much like a shopping cart, except nothing is purchased. Adding a training does **not** book it; booking happens when the user submits a request from this tab. It uses View → Controller → Service layering, like Courses.

- **Service** (`Services/TrainingListService.swift`): `TrainingListServiceProtocol` has one implementation, `TrainingListService`. It stores `[TrainingListItem]` as JSON at `fileURL`, which defaults to `Application Support/booked-courses.json` (`defaultFileURL`); tests pass a temporary location. It behaves like a backend: every call starts with a hardcoded 1-second dummy sleep, and failures throw `ServiceError` (`LocalizedError`): `.unreadable` when the file can't be read or decoded, `.saveFailed` when a write fails. The service owns all cart logic: `fetch()` returns an empty list if the file doesn't exist yet and throws `.unreadable` if it can't be decoded; `add` and `remove` instead treat an unreadable file as empty and overwrite it, so a bad file can't block the list (see `docs/decisions/0014-training-list-failures.md`); a private `save(_:)` writes atomically; `add(_:)` ignores duplicates (by `id`) and `remove(ids:)` removes matches. Both read the file, save right away and return the updated list. Every call returns a `TrainingList` (`Services/TrainingList.swift`): the items plus a `Summary` of count, hours and days. The service calculates the summary, with days = hours ÷ `hoursPerDay` (8). That value is a product rule (one training day is 8 hours), so it lives with the other cart rules (see `docs/decisions/0009-summary-in-service.md`). This is where a backend would plug in: it would take over the rules and the summary by implementing the protocol, with no change to the controller or views.
- **Model** (`Services/TrainingListItem.swift`): `TrainingListItem` is a slim snapshot of the `Course` fields Book displays (`id`, `name`, `subtitle`, `category`, `hours`), built with `init(_ course:)` when a course is added. It's Book's own save format, so changes to `Course` can't break saved lists. Showing a new course field in Book means adding it here (see `docs/decisions/0008-store-slim-cart-snapshots.md`).
- **Booking service** (`Services/BookingService.swift`, `Services/BookingRequest.swift`): `BookingServiceProtocol.submit(_:)` sends a `BookingRequest` (course IDs, contact details, preferred start date, notes) and returns a `BookingConfirmation` with a reference number. The only implementation is `MockBookingService`, which sleeps for `delay` and returns a generated `GC-XXXXXX` reference, or throws when `shouldFail` is set (for previews and tests). This is where a real backend would plug in.
- **Controller** (`Controller/TrainingListController.swift`): an `@Observable` class with no `@MainActor`, because of default isolation. The service is injected through `init` and is `@ObservationIgnored`. Its only output is `private(set) var state: LoadState<TrainingList>` (the shared enum in `Shared/LoadState.swift`). Every call (`fetch()`, `add(_:)`, which takes a `Course` and maps it to a `TrainingListItem`, and `remove(ids:)`) sets `.loading`, then `.success` with the list the service returned, or `.error(localizedDescription)`. There is no `list`, `items` or `contains` on the controller: they would read as empty mid-call, so views keep the last `.success` list themselves (see `docs/decisions/0014-training-list-failures.md`). Views call it inside `Task { await ... }`.
- **Shared state:** the `App` (`GetCertified.swift`) owns a single `TrainingListController` as `@State`. It injects it with `.environment(_:)` and loads it in `.task` at launch. Views read it with `@Environment(TrainingListController.self)`. Previews must inject one, too. Each view that shows the list stores what it needs from the last `.success` in its own `@State`, updated in `.onChange(of: controller.state, initial: true)`, so a later `.loading` or `.error` never clears it. A view reports an `.error` in an alert only after a change it started itself, by checking `state` after awaiting the call, so one failure doesn't raise alerts in several tabs.

## View

- `BookView` keeps `@State private var list: TrainingList?`, `nil` until the first `.success`. While `controller.state` is `.loading`, a loading overlay (a dimmed `ProgressView` that blocks touches) covers the content, including during a swipe-to-delete. With no list yet, `.error` shows a "Couldn't Load Training List" `ContentUnavailableView` with the message and a "Try Again" button that fetches again. Once a list is kept, a failed delete shows a "Couldn't Update Training List" alert over it. It lists the kept list's items.
- A "Submit Request" button sits in a bottom `safeAreaInset` above the tab bar. It presents `SubmitRequestView` as a sheet. The `.sheet` is attached at the top of `body`, not to the list, so it stays presented when the training list empties after a successful submit.
- Rows are removed with swipe-to-delete (`onDelete`), which calls `remove(ids:)` right away. There is no confirmation, no per-row button, and no Edit mode (see `docs/decisions/0011-swipe-only-removal.md`).
- With no items, the view shows `ContentUnavailableView`.

## Submit Request

- `SubmitRequestView` owns a `SubmitRequestController` as `@State`, created once from the training list (`controller.list`, items and summary) at presentation, and takes the booking service as an init parameter (defaults to `MockBookingService()`).
- `SubmitRequestController` holds the form fields and a `status`: `.editing`, `.submitting`, `.submitted(BookingConfirmation)` or `.failed(String)`. `canSubmit` requires at least one course, a non-empty name and a valid email. Phone, company and notes are optional. The preferred start date defaults to a week out and can't be earlier than tomorrow. Inputs are trimmed when the request is built.
- The form has three sections: Trainings (read-only, with a footer built from the passed-in summary), Contact, and Schedule. While submitting, the Submit toolbar button becomes a `ProgressView`, and the form and swipe-to-dismiss are disabled. A failure shows an alert and returns to the form with the input kept.
- On success, the view clears the submitted items from the training list with `TrainingListController.remove(ids:)` and swaps the form for a confirmation (`ContentUnavailableView` with the reference number and a Done button).
